# Native Bilibili public videos

The original C# provider reads Bilibili's public video and playback responses and uses the existing native HTTP and ffmpeg pipeline. It does not execute Python, yt-dlp, browser scripts or another site's extraction library.

## Implemented scope

- Public BV and AV video URLs, mobile and `/s/video/` aliases, and `player.bilibili.com/player.html` embeds. Conflicting identifiers and part parameters fail. Returned BV/AV identities and selected CID are verified.
- Complete bounded multipart inventories with unique CIDs, consecutive part positions and declared counts. A root multipart URL lists its parts. An explicit `p`, player `page` or `cid` selects one part; disabling playlist downloads selects the first part. Playback lookup happens only for selected parts.
- Public `x/web-interface/view` metadata and `x/player/playurl` media responses. Titles, descriptions, uploader, cover and part durations are retained. The native user agent identifies the engine; explicit user agent and referrer settings take precedence and the HTTP session remains shared.
- Offered clear MP4 DASH representations are complete HTTP resources containing initialization and media fragments. Video and AAC audio roles stay separate until native selection and ffmpeg merging. Actual dimensions, codecs, bitrate and frame rate come from each representation. Quality labels and accepted-quality lists do not create unavailable formats.
- Representations of the same CID share their original timestamp origin during merging. This preserves presentation offsets between video and audio rather than independently resetting each track to zero. The shared merger now rejects error-level ffmpeg diagnostics even if the process exits successfully; stream-copy mode can otherwise tolerate and publish damaged packets.
- Primary signed resource addresses retain their query bytes. The currently observed `upgcxcode` layout is bound to the selected CID. Known Bilibili CDN origins and its observed `upos-` Akamai origins are accepted. Unrecognized layouts fail explicitly; backup URLs are not used after access denial.
- Complete MP4/FLV `durl` responses may contain one file or an ordered chunk list. Multi-file responses expose one `http_sequence` format, with bounded parallel downloads, source-size/decoder checks and compatible joining before publication. The first chunk is never offered as the complete video. See `HTTP-SEQUENCES.md` for timeline, retention and verification details.
- Selected MP4/FLV files, including individual video-only and audio-only tracks, are fully decoded with the retained ffmpeg tool before publication. This is also done before downloading a companion track. A fixed local demuxer, disabled external MP4 references and restricted protocols keep text/playlist responses from being interpreted as media instructions. Missing ffmpeg fails before media transfer; simulation and existing-file/archive skips still work without it.
- Verification requires every declared media role to produce decoded packets and compares the final decoded timeline with the supplied complete playback duration, allowing 1.1 seconds for endpoint/encoding differences. It rejects decoder errors, empty initialization-only files, wrong media roles and materially short resources. It does not rewrite the source. FLV verification preserves the demuxer's frame time base so the verifier itself does not introduce timestamp-rounding errors.
- Part-specific native archive records use `bilibili <BVID>_<CID>`. Metadata discovery currently precedes archive checks, but archived media is not transferred again. This identity is not a claim of compatibility with all upstream archive variants.

Paid/member/exclusive/interactive/preview/live/DRM flags, non-public upload state, API errors and mismatched inventories fail explicitly. Playback duration is checked against the selected part with tolerance for rounded metadata. Unsupported video codecs cannot turn a video request into a successful audio-only download. No account acquisition, purchase or access-control workaround is implemented.

## Verification

Eighteen deterministic checks cover aliases, multipart inventory and simulation/selection, embed dispatch, offered format facts and query parameters, archives, caller headers, preview/access failures, malformed identities/representations, resource boundaries, tool preflight, no-overwrite behavior and cancellation. Canceling during verification kills and drains the actual child process before returning, preserving published files and avoiding archive entries or completion callbacks.

Twelve generated-media checks exercise complete fragmented-MP4 video and audio resources through the native provider. Combined, video-only and audio-only outputs retain every source frame and fully decode. Combined processing preserves original component bytes, merged originals, metadata, part identity, source timing and completion callbacks. Damaged video/audio, empty initialization, wrong-role media and a decodable but too-short file are rejected without changing prior outputs or archives. Additional real MP4/FLV and selected-part tests verify exact source-byte preservation, literal access parameters, caller headers, playlist identity and archive skips.

The ordered-file extension adds five deterministic checks and eleven generated-media checks for complete sequences, compatible MP4/FLV joins, all retained frames, decoded video-frame order, source retention, parallel completion, retries, failures and cancellation. See `HTTP-SEQUENCES.md` for the longer real-media replay and its limits.

The live public sample is [Big Buck Bunny, BV1Zs411o7Ee](https://www.bilibili.com/video/BV1Zs411o7Ee/), a two-part Blender film upload. The first part downloaded completely at 852x480 with H.264 video and AAC audio. Replaying its retained original tracks through the corrected native merge produced a 63,940,756-byte processed MP4 lasting 596.624 seconds. Both the processed and retained files fully decoded, preserving 14,317 video frames and 27,966 audio frames. Every packet's presentation time, decode time and payload hash matched the respective source, including the original 83-millisecond video offset.

The second part's initial transfer ended prematurely. A normal retry completed the transfer, but independent decoding found corrupt video packets. Its recorded media now fails the native merge with no published files, archive entries or completion callbacks. The cause of that source/transfer corruption and successful second-part live playback remain unverified. A completed HTTP transfer alone is not used as playback verification.

On version 0.47.0, the complete retained first-part tracks were replayed through the provider and new decoder verification before merging. The output remained the same 63,940,756 bytes with four completed media outputs. The retained damaged second part was rejected before merging or companion-audio transfer, with zero publications, archive entries or callbacks. Fresh bounded checks matched the saved first 134,644 video bytes before the server again ended a response prematurely; the remaining source/transfer discrepancy is unresolved.

The verifier uses ffmpeg's documented [error and empty-output controls](https://ffmpeg.org/ffmpeg.html#Advanced-options). Decoding and declared-duration checks establish stronger playback evidence than byte counts alone; they are not a cryptographic source-integrity guarantee. Provider source hashes, broader transport/container validation and recovery from corrupt sources remain future work.
